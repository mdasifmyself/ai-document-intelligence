# Evaluation report

All numbers below were **measured on the running system** (the same deployment as the live demo) by
[`evaluation/run_eval.py`](../evaluation/run_eval.py), starting from an empty database and an empty AI answer cache.
Nothing is estimated. Raw results: [`evaluation/results/`](../evaluation/results/); earlier runs in
[`evaluation/results/history/`](../evaluation/results/history/).

## 1. Dataset

A labelled dataset of **96 files containing 141 invoices**, generated by [`dataset/generate.py`](../dataset/generate.py)
(fictional companies, seed 42) so that every value has a known correct answer. Details: [dataset/README.md](../dataset/README.md).

| Kind of file | Files |
|---|---|
| Digital PDFs (3 layouts, 4 currencies, different label wordings and date formats) | 30 |
| Digital PDFs with planted problems (wrong totals, wrong line amounts, missing date / customer / tax, ambiguous dates) | 19 |
| Scanned PDFs (rotation, noise, blur, JPEG artefacts) | 12 |
| Phone photos (perspective, shadow, blur) · very poor photos · clean PNG | 8 · 4 · 5 |
| Multi-page TIFF (2 invoices each) · batch PDFs (6 invoices each, one spanning 2 pages) | 2 · 2 |
| Duplicates (re-sent PDF, scanned copy) · conflicting revision of an invoice | 2 · 1 |
| Excel ledger (3 sheets, cross-checks 14 PDF invoices, 3 with different totals, a duplicate row, a missing number, a wrong total) | 1 |
| Legacy XLS · US CSV · EU CSV (`;`, decimal comma) · invoice laid out in a spreadsheet | 1 · 1 · 1 · 1 |
| Broken or locked (truncated PDF, random bytes, empty PNG, cut XLSX, password PDF, text renamed .jpg) | 6 |

Plus a **1,000-page batch PDF holding 789 invoices** (1–3 pages each) for speed and accuracy at scale.

## 2. Method

1. Upload every file through the public API (as a user would), in batches of 12.
2. Wait for the background workers (2 workers on a small 2-CPU server shared with other services).
3. Fetch every result and compare each field with the answer key:
   * invoice number: equal after removing spaces and punctuation;
   * date: equal (ISO); an ambiguous printed date must come back empty and flagged;
   * supplier / customer: ≥ 90 % similar after removing legal suffixes (Ltd, LLC…);
   * amounts: within 0.01; currency: same ISO code;
   * a field that is not printed must come back **empty** (anything else counts as an invented value).
4. Check that each planted problem was flagged on the right invoice, and count flags on clean invoices.
5. Time every document (from the start of processing to the end) and the whole run.

## 5. Run history: what each run found and what was fixed

The evaluation was run repeatedly; every problem it revealed was traced to its root cause, fixed, covered by a test,
and measured again.

| Run | Field accuracy | All fields right | Line items | No invented values | Planted caught | What the run revealed → fix |
|---|---|---|---|---|---|---|
| 1 | 97.4 % | 94.3 % | 96.9 % | 90.9 % | 43 / 51 | percentage rounding tolerance hid wrong totals on large amounts → absolute tolerance; duplicate flag on the first copy → later copy; an ambiguous date guessed → always flagged; OCR values unproven → wider image re-read |
| 2 | 99.6 % | 98.6 % | 95.9 % | 100 % | 55 / 55 | readings that agree should confirm a value → two-reading agreement |
| 3 | 99.8 % | 99.3 % | 95.9 % | 100 % | 55 / 55 | an OCR "3" read as "2" was copied by the image re-read → image reading made fully independent; occasional 502s → keep-alive fix and proxy-label fix |
| 4 | 100.0 % | 100.0 % | 95.9 % | 100 % | 55 / 55 | dual reading for every scan; an empty line-item list could "win" → complete items always preferred |
| 5 | (stopped) |  |  |  |  | 42 files failed with a database error after a worker restart → forked jobs now never reuse the parent's connections (regression test added) |

## 6. What the numbers do and do not show

* The dataset is synthetic. It is varied (layouts, currencies, scans, photos, blur, rotation, broken files, planted
  errors), but real invoices from many suppliers will be harder. That is why the system flags uncertainty instead of
  guessing, and why every value carries its proof.
* "100 % field accuracy" means every value was right **or correctly left empty** on this set. It does not mean the
  model cannot make mistakes: on very poor photos it occasionally misreads a value, and in those cases the invoice is
  always sent to a person (4 of 4 poor photos in the review queue).
* Speed is limited mainly by the AI provider's rate limit and the small shared server (2 CPUs). It scales with more
  workers and a higher API tier ([02-architecture.md](02-architecture.md#scaling)).
